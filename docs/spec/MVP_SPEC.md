# MVP Spec

## 系统目标

RMA Trace 是一个五人数据库课程项目。系统需要证明以下内容：

1. 数据库关系、主外键和约束能够解释。
2. 前端页面通过 Spring Boot API 真实查询和修改 MySQL 数据。
3. 一条售后主演示链可以从头运行到结案。
4. 五位成员均有可审核的数据库、代码、测试和讲解内容。

第一版不追求模拟完整企业售后系统。出现进度冲突时，优先保证数据库设计、演示数据、跨表查询和主演示链。

## 范围分级

### 必做

- 九张业务表、总 ER 图、字段说明、主外键和完整性约束
- `sql/schema.sql` 与 `sql/demo-data.sql`
- 固定演示账号登录及客服、维修人员、管理员三个角色
- 产品型号、生产批次、产品实例的数据管理
- 客户新增、查询和修改
- 根据 SN 查询产品与保修状态
- 创建、受理和拒绝售后申请
- 受理申请后生成 RMA
- 每张 RMA 最多登记一次检测和一次维修
- RMA 结案
- 根据 SN 查询型号、批次、申请、故障判断和维修结果
- 五个模块页面
- 每位成员至少一条手写业务 SQL、测试证据和独立 PR

### 选做

- 换新流程
- 零件批次及生产用料关系
- 从生产批次反查全部产品
- 多次检测、返修和任意状态回退
- 动态角色与权限管理
- 删除业务数据
- RMA 状态人工修正
- 工作台统计、图表和动画
- 操作日志和状态历史

选做内容不能影响必做内容的进度。未经全组确认，不提前加入第一版数据库。

## 用户角色

### 客服

- 查询产品 SN 和保修状态
- 新增或修改客户资料
- 创建、受理或拒绝售后申请
- 查询 RMA 当前状态
- 对待结案 RMA 执行结案

### 维修人员

- 查看待检测或待维修 RMA
- 登记检测结果和故障类型
- 登记维修方式和维修结果

### 管理员

- 维护产品型号、生产批次和产品实例
- 查看所有业务数据
- 查看产品追查结果

第一版不提供管理员任意修改业务状态的特殊入口。

## 主演示链

```text
管理员维护产品型号、生产批次和产品实例
→ 客服输入 SN 查询产品和保修状态
→ 客服选择客户并创建售后申请
→ 客服受理申请并生成 RMA
→ 维修人员登记检测结果
→ 维修人员登记维修结果
→ 客服完成结案
→ 管理员按 SN 查看生产批次和售后处理结果
```

## 核心用例

### UC-01 管理产品数据

**参与者：** 管理员

**处理：** 新增、查询和修改产品型号、生产批次及产品实例。

**约束：** 产品 SN、型号编号和生产批次编号必须唯一；第一版不提供删除操作。

### UC-02 查询产品与保修

**参与者：** 客服、管理员

**输入：** 产品 SN

**输出：** 产品实例、型号、生产批次、销售日期和当前保修状态。

**异常：** SN 不存在时显示明确提示，不创建业务记录。

### UC-03 管理客户并创建售后申请

**参与者：** 客服

**前提：** 客户和产品实例存在。

**输入：** 客户、产品 SN、问题描述。

**输出：** 状态为待受理的售后申请。

**约束：** 同一产品存在未结束售后流程时，不允许再次创建申请。

### UC-04 受理或拒绝售后申请

**参与者：** 客服

**前提：** 售后申请状态为待受理。

**处理：** 客服选择受理或拒绝。受理时创建唯一 RMA，拒绝时不创建 RMA。

**异常：** 已受理或已拒绝的申请不能再次处理。

### UC-05 检测产品

**参与者：** 维修人员

**前提：** RMA 状态为待检测，且尚无检测记录。

**输入：** 故障类型和检测说明。

**输出：** 一条检测记录，RMA 状态变为待维修。

### UC-06 维修产品

**参与者：** 维修人员

**前提：** RMA 状态为待维修，且存在检测记录、尚无维修记录。

**输入：** 维修方式、维修结果和必要说明。

**输出：** 一条关联检测记录的维修记录，RMA 状态变为待结案。

维修失败不增加新状态，在维修结果中记录原因，之后仍由客服结案。

### UC-07 结案

**参与者：** 客服

**前提：** RMA 状态为待结案。

**输出：** RMA 状态变为已结案。

**约束：** 已结案 RMA 不能新增检测或维修记录。

### UC-08 产品追查

**参与者：** 管理员

**输入：** 产品 SN

**输出：** 产品型号、生产批次、售后申请、RMA、故障判断和维修结果。

**查询要求：** 使用手写多表 SQL，保留可在答辩中展示的查询语句。

## 状态规则

### 售后申请

```text
待受理 → 已受理
待受理 → 已拒绝
```

### RMA

```text
待检测 → 待维修 → 待结案 → 已结案
```

- 创建 RMA 时状态为待检测。
- 创建检测记录时进入待维修。
- 创建维修记录时进入待结案。
- 客服确认后进入已结案。
- 第一版不实现回退和人工修正。

## 九张表与负责人

| 负责人 | 表 | 业务含义 |
|---|---|---|
| B | `app_user` | 系统登录账号及固定角色 |
| B | `rma_order` | 售后申请受理后生成的正式处理单 |
| C | `product_model` | 产品型号及默认保修月数 |
| C | `production_batch` | 一个型号的一次生产批次 |
| C | `product_instance` | 通过唯一 SN 识别的具体产品 |
| D | `customer` | 提出售后申请的客户 |
| D | `service_request` | 客户提交、等待客服处理的问题记录 |
| E | `inspection_record` | 维修人员的故障判断和检测说明 |
| E | `repair_record` | 针对检测结果执行的维修及其结果 |

A 不负责额外业务表的首稿。A 主持关系检查，汇总总 ER 图、`schema.sql` 和 `demo-data.sql`。

## 实体关系骨架

```text
product_model 1 ── N production_batch
production_batch 1 ── N product_instance

customer 1 ── N service_request
product_instance 1 ── N service_request
service_request 1 ── 0..1 rma_order
rma_order 1 ── 0..1 inspection_record
inspection_record 1 ── 0..1 repair_record
```

关键操作人来自 `app_user`：

- 售后申请记录创建人和处理人。
- RMA 记录受理人和结案人。
- 检测记录保存检测人。
- 维修记录保存维修人。

各模块负责人在骨架上补充字段。不得自行增加跨模块外键；新增关系先由 A 检查。

## 保修计算

- `product_model` 保存默认保修月数。
- `product_instance` 保存销售日期。
- 当 `销售日期 <= 当天 < 销售日期 + 保修月数` 时，产品在保。
- 没有销售日期时显示“尚未销售或无法判断”，不判定为在保。
- 第一版不支持单个产品覆盖型号默认保修月数。

## 标识与完整性

### 标识

- 每张表使用内部数字主键 `id`。
- `app_user.username` 唯一。
- `product_model.model_code` 唯一。
- `production_batch.batch_no` 唯一。
- `product_instance.serial_number` 唯一。
- `rma_order.rma_no` 唯一。
- 售后申请、检测记录和维修记录直接使用数字 ID，不额外生成业务编号。

### 数据库约束

- 所有主键非空且唯一。
- 关键业务关系使用外键。
- 保修月数必须大于或等于零。
- 售后申请和 RMA 状态只能取预设值。
- `rma_order.service_request_id` 唯一，保证一份申请最多生成一张 RMA。
- `inspection_record.rma_order_id` 唯一，保证一张 RMA 最多一条检测记录。
- `repair_record.inspection_record_id` 唯一，保证一条检测记录最多一条维修记录。
- 已被引用的数据不允许删除，外键删除行为使用限制删除。

### Service 层规则

- 同一产品存在待受理申请或未结案 RMA 时，不允许再次创建申请。
- 只有待检测 RMA 可以新增检测记录。
- 只有待维修 RMA 可以新增维修记录。
- 只有待结案 RMA 可以结案。
- 状态变更和对应业务记录写入应在同一事务中完成。

## 页面清单

第一版使用五个页面或五个清楚区分的页面入口：

1. 登录页
2. 产品数据管理与 SN 查询页
3. 客户与售后申请页
4. RMA、检测与维修处理页
5. 产品追查页

页面必须真实调用 API 和 MySQL。不得使用前端写死数据代替数据库结果。

## API 范围

接口统一使用 `/api` 前缀和 JSON。以下按业务能力分组，具体请求字段由负责人补充接口示例。

```text
登录：登录、获取当前用户
产品型号：查询、新增、修改
生产批次：查询、新增、修改
产品实例：查询、新增、修改、按 SN 查询保修、按 SN 追查
客户：查询、新增、修改
售后申请：查询、新增、受理、拒绝
RMA：查询详情、查询待处理列表、结案
检测：为待检测 RMA 新增检测记录
维修：为检测记录新增维修记录
```

接口响应格式由 B 给出统一示例。C、D、E 不得设计互不兼容的返回格式。

## 验收场景

### 场景一：管理产品数据

管理员新增产品型号、生产批次和具有唯一 SN 的产品实例，刷新页面后数据仍来自 MySQL。

### 场景二：查询保修

输入存在的产品 SN，页面正确显示型号、生产批次、销售日期和保修状态。

### 场景三：创建并受理申请

客服为客户创建售后申请并受理，数据库新增申请和 RMA，页面显示唯一 RMA 编号。

### 场景四：检测、维修和结案

维修人员登记检测与维修结果，客服完成结案，数据库记录和页面状态一致。

### 场景五：拒绝非法操作

系统拒绝重复受理、重复检测、重复维修、已结案后继续写入，以及同一产品同时创建多个未结束流程。

### 场景六：产品追查

输入产品 SN，系统展示型号、生产批次、售后申请、故障判断和维修结果。

### 场景七：角色限制

客服不能维护产品批次，维修人员不能受理申请，普通业务操作不能绕过角色检查。

## 演示方案

五分钟只演示一条故事：

```text
管理员展示预先准备的产品数据
→ 客服查询在保产品并创建、受理申请
→ 维修人员登记检测和维修结果
→ 客服完成结案
→ 管理员按 SN 展示跨表追查结果
```

演示前准备固定账号、产品、客户和批次数据。页面操作出现异常时，使用备用视频和截图继续讲解。
