# MVP Spec

## 系统说明

系统面向消费电子企业的客服、维修人员和管理员。它管理产品 SN、保修、售后申请、RMA、故障检测、维修、换新和产品批次追查。

第一版只保证一条主流程和一条追查链可以运行。其他功能不能影响 10 月 23 日的现场演示。

## 用户角色

### 客服

- 查询产品 SN 和保修状态
- 登记客户与售后申请
- 审核申请并创建 RMA
- 查询 RMA 当前状态

### 维修人员

- 查看待检测 RMA
- 登记检测结果和故障类型
- 登记维修处理与结果
- 提交维修完成状态

### 管理员

- 查看所有业务数据
- 维护产品型号、生产批次和零件批次
- 查看产品追查结果
- 管理演示账号和基础数据

## 核心用例

### UC-01 查询产品

**参与者：** 客服、管理员

**输入：** 产品 SN

**处理：** 查询产品实例、型号、销售日期和保修期限。

**输出：** 产品信息、是否在保、是否存在处理中 RMA。

**异常：** SN 不存在时显示明确提示，不创建任何业务记录。

### UC-02 创建售后申请

**参与者：** 客服

**前提：** 客户与产品存在。

**输入：** 客户、产品 SN、问题描述、申请时间。

**输出：** 待受理的售后申请。

**约束：** 同一产品存在处理中 RMA 时，不允许再次创建相同类型的售后流程。

### UC-03 受理并创建 RMA

**参与者：** 客服

**前提：** 售后申请状态为待受理。

**输入：** 申请编号、受理意见。

**输出：** 唯一 RMA 编号，申请状态改为已受理。

**异常：** 已拒绝或已受理的申请不能再次生成 RMA。

### UC-04 检测与维修

**参与者：** 维修人员

**前提：** RMA 已进入待检测状态。

**输入：** 故障类型、检测说明、维修方式、维修结果。

**输出：** 检测记录和维修记录，RMA 状态随业务推进。

**异常：** 已结案 RMA 不能新增维修记录。

### UC-05 换新或结案

**参与者：** 管理员或拥有对应权限的客服

**前提：** 产品已经检测。

**处理：** 根据维修结果选择完成维修、换新或无法处理。

**输出：** 结案结果；换新时记录原 SN 与新 SN 的关系。

### UC-06 产品追查

**参与者：** 管理员

**输入：** 产品 SN 或零件批次编号。

**输出：** 产品型号、生产批次、使用的零件批次及关联售后故障。

**查询要求：** 使用手写多表 SQL，保留可在答辩中展示的查询语句。

## 状态规则

### 售后申请

```text
待受理 → 已受理
待受理 → 已拒绝
```

### RMA

```text
待检测 → 检测中 → 维修中 → 待结案 → 已结案
                  ↘ 待换新 → 已结案
```

第一版不实现任意回退。确有演示需要时，由管理员进行明确的修正操作并记录原因。

## 数据对象

以下清单用于指导模块 ER 图。最终字段由模块负责人提出，A 检查后写入总结构。

### 产品与保修

- `product_model`：产品型号
- `production_batch`：生产批次
- `component_batch`：零件批次
- `batch_component_usage`：生产批次使用零件批次的关系
- `product_instance`：具有唯一 SN 的产品实例
- `warranty_policy`：型号对应的保修政策

### 客户与售后

- `customer`：客户基本信息
- `service_request`：客户提交的售后申请
- `rma_order`：正式受理后的 RMA

### 检测与维修

- `fault_category`：故障分类
- `inspection_record`：检测记录
- `repair_record`：维修记录
- `replacement_record`：换新记录

### 用户权限

- `app_user`：系统用户
- `app_role`：客服、维修人员、管理员
- `user_role`：用户与角色关系

是否增加状态历史、操作日志等表，由课程要求和剩余时间决定，不能影响主流程。

## 关系要求

- 一个产品型号可以对应多个产品实例。
- 一个产品实例只有一个唯一 SN。
- 一个生产批次可以生产多个产品实例。
- 一个生产批次可以使用多个零件批次，一个零件批次也可以被多个生产批次使用。
- 一个客户可以提交多个售后申请。
- 一个售后申请最多生成一个 RMA。
- 一个 RMA 可以具有检测记录和维修记录。
- 一次换新必须关联原产品与新产品。

## 完整性规则

数据库至少实现以下约束：

- 所有主键非空且唯一。
- `serial_number` 唯一。
- `rma_no` 唯一。
- 关键业务关系使用外键。
- 保修期限不能为负数。
- 申请状态和 RMA 状态只能取预设值。
- 已结案 RMA 不允许新增检测或维修记录。
- 新旧换新产品不能是同一 SN。
- 同一售后申请不能生成多个 RMA。

无法直接使用 MySQL `CHECK` 表达的跨表规则，可以在 Service 层完成；答辩时必须说明规则在哪一层执行。

## 页面清单

页面保持极简，只要求清楚、可操作、能展示数据库变化。

1. 登录页
2. 工作台
3. 产品与保修查询页
4. 客户列表与编辑页
5. 售后申请列表与表单页
6. RMA 详情与状态操作页
7. 待检测列表
8. 检测与维修登记页
9. 产品追查页

工作台只显示少量统计数字。图表、动画和复杂响应式布局不属于 MVP。

## API 约定

统一使用 `/api` 前缀和 JSON。

```text
GET    /api/products/{sn}
GET    /api/products/{sn}/trace
GET    /api/customers
POST   /api/customers
GET    /api/service-requests
POST   /api/service-requests
POST   /api/service-requests/{id}/accept
POST   /api/service-requests/{id}/reject
GET    /api/rmas
GET    /api/rmas/{id}
POST   /api/rmas/{id}/inspections
POST   /api/rmas/{id}/repairs
POST   /api/rmas/{id}/replace
POST   /api/rmas/{id}/close
```

接口响应格式由 B 给出统一示例，C、D、E 不得为各自模块设计互不兼容的返回格式。

## 验收场景

### 场景一

输入存在且在保的产品 SN，页面正确显示型号、销售时间和保修状态。

### 场景二

客服创建售后申请并受理，数据库新增申请和 RMA，页面显示新的 RMA 编号。

### 场景三

维修人员登记故障、检测和维修结果，数据库记录与页面显示一致。

### 场景四

对已结案 RMA 再次提交维修记录，系统拒绝操作并显示原因。

### 场景五

输入产品 SN，系统展示生产批次、零件批次和售后故障。

### 场景六

客服账号无法进入管理员功能，维修账号无法受理售后申请。

## 演示方案

五分钟只演示一条故事：

```text
查询一个在保产品
→ 创建售后申请
→ 受理并生成 RMA
→ 切换维修角色登记故障和结果
→ 完成结案
→ 查询该产品的生产与零件批次
```

演示前准备好账号、产品、客户和批次数据。页面操作出现异常时，使用备用视频和截图继续讲解。
