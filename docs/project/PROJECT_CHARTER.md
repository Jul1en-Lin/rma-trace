# 项目章程

## 项目信息

**项目名称：** 消费电子产品售后维修与产品追溯管理系统

**项目类型：** 五人数据库课程设计

**项目目标：** 完成一个可运行的 Web 系统，以九张关系表为基础，通过前端页面和 Spring Boot API 真实查询、增加和修改 MySQL 数据，并在五分钟内演示一条完整售后流程。

**完成标准：** 数据库关系、主外键和约束能够解释；主演示链可以运行；五个人均有可审核的表设计、代码、测试、PR 和讲解内容。

## 项目范围

### 售后主演示链

```text
产品 SN 与保修查询
→ 创建售后申请
→ 客服受理并生成 RMA
→ 维修人员登记检测结果
→ 维修人员登记维修结果
→ 客服结案
```

### 产品追查

```text
产品型号
→ 生产批次
→ 产品 SN
→ 售后申请
→ 故障判断与维修结果
```

产品追查只实现按 SN 查询，不延伸为完整生产或零件追溯系统。

## 第一版不做

- 换新、返修和多次检测
- 零件批次及生产用料关系
- 从生产批次反查全部产品
- 供应商、仓储、物流、退款和生产排程
- 动态角色和权限配置
- 删除业务数据和任意修改业务状态
- 操作日志、状态历史、复杂统计和图表
- 用户注册、找回密码、短信、邮件和移动端应用

这些内容可以作为选做，但不能影响数据库、主演示链和课程交付。

## 数据库设计

第一版只包含九张表：

```text
app_user
product_model
production_batch
product_instance
customer
service_request
rma_order
inspection_record
repair_record
```

先由全组确认实体关系骨架，再由 B、C、D、E 分别补充本人负责表的字段。A 检查跨模块关系、主外键、唯一约束和完整性，并汇总总 ER 图与 SQL。

数据库只维护当前可用版本：

```text
sql/
├── schema.sql
└── demo-data.sql
```

- `schema.sql` 保存当前完整表结构。
- `demo-data.sql` 保存贯穿主演示链的固定数据。
- 表结构调整后，成员清空本地数据库并导入当前 SQL。
- 已被引用的数据不允许删除。
- 跨表业务规则无法直接由数据库表达时，在 Service 层校验并使用事务。
- 个人数据库账号和密码不得提交到仓库。

## 技术方案

```text
浏览器：HTML + CSS + 原生 JavaScript + Bootstrap
数据请求：Fetch API
服务端：Java + Spring Boot
数据访问：MyBatis-Plus
数据库：MySQL 8
项目管理：Maven
协作：Gitee Issues + Fork + Pull Request
```

MyBatis-Plus 用于普通单表操作；跨表查询、产品追查和统计查询使用 Mapper XML 或手写 SQL。项目保留 Controller、Service、Mapper 三层。

## 页面范围

第一版只提供五个页面或五个页面入口：

1. 登录页
2. 产品数据管理与 SN 查询页
3. 客户与售后申请页
4. RMA、检测与维修处理页
5. 产品追查页

业务记录通过流程产生，不提供可以绕过状态规则的通用编辑页面。

## 团队原则

- 每张表只有一个字段初稿负责人。
- B 负责 `app_user`、`rma_order`。
- C 负责 `product_model`、`production_batch`、`product_instance`。
- D 负责 `customer`、`service_request`。
- E 负责 `inspection_record`、`repair_record`。
- A 负责总数据库检查和合并，不额外承担无人负责的业务表。
- 每位模块负责人都参与表设计、后端、页面、测试和讲解。
- 进度受阻时先删除选做内容，再保证数据库和主演示链。
- B、C、D、E 通过个人 Fork 和 PR 提交，A 使用 merge commit 合并。

## 成功条件

1. 能从统一 SQL 文件初始化 MySQL 数据库。
2. 页面能通过 Spring Boot API 查询、增加和修改数据库数据。
3. 三个角色具有不同操作范围。
4. 售后申请和 RMA 状态不能任意跳转。
5. 总 ER 图、模块 ER 图、字段说明和最终表结构一致。
6. 五位成员均有独立 PR、SQL、测试证据和答辩内容。
7. 五分钟演示能够完整走通预定业务链。
