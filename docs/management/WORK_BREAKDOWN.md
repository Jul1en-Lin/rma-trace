# 五人任务包

## 分工原则

每个人负责一段可以独立验收的业务功能。模块负责人同时参与表设计、后端、页面、测试和讲解。

A 负责总数据库的一致性，不代替其他成员完成模块表设计。B 负责公共后端约定，不代替 C、D、E 编写全部 Service 和 Mapper。

## A 任务包

**职责：** 需求、数据库总设计、界面规范、产品追查、Git 审核、最终集成。

**设计产出：**

- 项目范围与需求文档
- 总 ER 图
- 数据表命名与字段规范
- 主外键和完整性检查
- 当前 `schema.sql` 与 `demo-data.sql`
- 页面布局和组件规范

**代码产出：**

- 产品 SN 追查接口
- 产品追查页面
- 多表追查 SQL
- 集成分支和发布版本

**验收：**

- 所有模块表可以通过统一 SQL 创建。
- 总 ER 图与实际表结构一致。
- 能从 SN 查到生产批次、零件批次和售后故障。
- 所有合并 PR 均有审核记录。

## B 任务包

**职责：** 公共 Spring Boot 代码、登录权限、RMA 流程、换新与结案、后端审查。

**设计产出：**

- 公共包结构和编码示例
- 统一接口响应与异常格式
- RMA 状态图和状态规则
- 登录与角色权限说明

**代码产出：**

- Spring Boot 初始项目
- MyBatis-Plus 和 MySQL 配置示例
- 登录与三个角色的权限校验
- RMA 受理后的状态操作
- 换新与结案接口及页面

**验收：**

- 三个角色的操作范围不同。
- 非法状态跳转被拒绝。
- C、D、E 可以参照公共示例开发自己的模块。
- 完成对 E 模块的定期代码审查。

## C 任务包

**职责：** 产品型号、产品 SN、保修查询。

**设计产出：**

- 产品与保修模块 ER 图
- 字段清单、主外键和业务规则
- 产品查询接口说明

**代码产出：**

- 产品型号与产品实例的 Controller、Service、Mapper
- SN 与保修查询 API
- 产品与保修查询页面
- 单表 CRUD 与一条保修业务查询

**验收：**

- 输入有效 SN 可以查到产品和保修信息。
- 输入不存在的 SN 得到明确提示。
- SN 唯一约束有效。
- 至少提交一个独立 PR，并能够现场解释代码与表关系。

## D 任务包

**职责：** 客户、售后申请、客服受理。

**设计产出：**

- 客户与售后申请模块 ER 图
- 字段清单、主外键和申请状态规则
- 售后申请接口说明

**代码产出：**

- 客户和售后申请的 Controller、Service、Mapper
- 售后申请创建、查询、受理和拒绝接口
- 客户与售后申请页面
- 一条查询客户历史申请的业务 SQL

**验收：**

- 可以为现有客户与产品创建售后申请。
- 申请可以受理或拒绝，处理完成后不能再次操作。
- 受理后能够调用 B 提供的流程创建 RMA。
- 至少提交一个独立 PR，并能够现场解释代码与表关系。

## E 任务包

**职责：** 检测、故障和维修记录。

**设计产出：**

- 检测与维修模块 ER 图
- 字段清单、主外键和维修规则
- 检测维修接口说明

**代码产出：**

- 故障分类、检测记录和维修记录的 Controller、Service、Mapper
- 待检测列表、检测登记和维修登记接口
- 检测与维修页面
- 一条按故障分类查询维修记录的业务 SQL

**验收：**

- 维修人员可以处理处于正确状态的 RMA。
- 检测与维修记录能正确关联 RMA 和产品。
- 已结案 RMA 不能新增记录。
- 至少提交一个独立 PR，并能够现场解释代码与表关系。

## 共同交付

每位成员的模块均需包含：

1. 模块 ER 图
2. 字段和业务规则说明
3. Controller、Service、Mapper
4. HTML、CSS、JavaScript 页面
5. 至少一条手写业务 SQL
6. 接口测试结果
7. 页面截图
8. 一个或多个关联 Issue 的 PR
9. 可独立讲解的答辩内容

## GitHub 工作流

```text
创建 Issue
→ 分配负责人
→ 负责人 Fork 上游仓库
→ 在个人 Fork 创建功能分支
→ 开发与本地测试
→ 推送到个人 Fork
→ 向 A 的上游仓库发起 PR 并关联 Issue
→ A 或 B 提出审核意见
→ 负责人修改
→ A 使用 merge commit 合并
→ 关闭 Issue
```

### 首次设置

成员 Fork 仓库后，只需设置一次远端：

```bash
git clone https://github.com/<成员用户名>/rma-trace.git
cd rma-trace
git remote add upstream https://github.com/<A用户名>/rma-trace.git
git remote -v
```

其中 `origin` 指向成员自己的 Fork，`upstream` 指向 A 的仓库。

### 开始任务

每次开始新 Issue 前先同步上游，再创建功能分支：

```bash
git switch main
git fetch upstream
git merge upstream/main
git push origin main
git switch -c feat/12-warranty-query
```

开发完成后推送到个人 Fork：

```bash
git push -u origin feat/12-warranty-query
```

随后在 GitHub 创建 PR：

```text
base repository: <A用户名>/rma-trace
base branch: main
head repository: <成员用户名>/rma-trace
compare branch: feat/12-warranty-query
```

成员不需要成为上游仓库 Collaborator。若 GitHub 无法把 Issue 直接分配给某位成员，A 在 Issue 正文中使用 `@用户名` 标注负责人。

### 分支命名

```text
feat/12-warranty-query
fix/27-rma-status-check
docs/31-er-diagram
```

### 提交信息

```text
feat: add warranty query API
fix: reject repair on closed RMA
docs: update customer module ER diagram
test: add service request validation cases
```

## 完成定义

一个 Issue 同时满足以下条件才能关闭：

- 功能符合验收条件。
- 页面可以真实读写 MySQL 数据。
- 后端包含必要校验和错误提示。
- 本人完成本地测试。
- PR 关联对应 Issue。
- A 或 B 完成代码审查。
- 表结构变化已经进入当前 `schema.sql`。
- 相关 ER 图和字段说明同步更新。

## 延期处理

成员遇到问题时按以下顺序处理：

```text
在 Issue 说明现象和已尝试内容
→ A 或 B 给出提示
→ 结对完成一个最小例子
→ 原负责人继续完成
→ 缩减次要内容
→ 仍影响主演示链时由 A 接管
```

A 接管时保留原 Issue 和 PR，说明原负责人已有产出、未完成原因和接管范围。原负责人继续参与测试和答辩准备。

## 五分钟演示

建议时间分配：

| 时间 | 内容 |
|---|---|
| 0:00—0:30 | 题目、角色和系统范围 |
| 0:30—1:00 | 总 ER 图与数据链 |
| 1:00—3:50 | SN 查询、申请、RMA、维修、结案、追查演示 |
| 3:50—4:30 | 完整性、权限和手写 SQL |
| 4:30—5:00 | 五人分工与 GitHub 贡献证据 |

GitHub 工作流用于证明协作过程，控制在最后半分钟内。系统功能、数据库关系和约束占主要时间。
