# 五人任务包

## 分工原则

项目先完成九张表的实体关系骨架，再由每张表的负责人补字段、模块 ER 图和业务规则。A 负责跨模块检查，不代替成员完成表设计。

每个人的必做交付包括：

1. 本人负责内容的设计说明
2. Controller、Service、Mapper 或跨表查询代码
3. 页面功能或页面协作内容
4. 至少一条手写业务 SQL
5. 接口测试结果和页面截图
6. 一个或多个关联 Issue 的独立 PR
7. 可独立讲解的答辩内容

## 表与模块分工

| 成员 | 表 | 功能 |
|---|---|---|
| A | 不负责额外业务表 | 总 ER、总 SQL、产品追查、集成与 PR 审核 |
| B | `app_user`、`rma_order` | 公共后端、登录权限、RMA 状态与结案 |
| C | `product_model`、`production_batch`、`product_instance` | 产品数据管理、SN 与保修查询 |
| D | `customer`、`service_request` | 客户、售后申请、受理与拒绝 |
| E | `inspection_record`、`repair_record` | 检测、维修及对应状态推进 |

个人边界和验收条件以 `docs/assignments/A.md` 至 `E.md` 为准。

## 页面分工

| 页面 | 负责人 |
|---|---|
| 登录页 | B |
| 产品数据管理与 SN 查询页 | C |
| 客户与售后申请页 | D |
| RMA、检测与维修处理页 | B、E |
| 产品追查页 | A |

页面使用同一套布局和响应格式，不按每张表分别制作 CRUD 页面。

## 依赖顺序

```text
全组确认实体关系骨架
→ B、C、D、E 并行提交字段初稿和模块 ER 图
→ A 检查并合并总 ER 图与 schema.sql
→ B 提供公共后端和接口示例
→ C、D、E 按模块开发
→ A、B 持续审核和联调
→ 全组准备固定演示数据与答辩材料
```

为减少等待：

- B 先提供统一响应、异常和事务示例。
- C 先提供可供联调的固定产品 SN。
- B 为 D 提供创建 RMA 的方法约定。
- B 为 E 提供 RMA 状态检查和推进方法约定。
- 模块开发可以使用 `demo-data.sql` 的固定外键数据，不必等待其他页面完成。

## Issue 拆分规则

一个 Issue 只负责一个能够单独验收的结果。Issue 必须写明：

- 业务目标和不包含的内容
- 涉及的表、约束和负责人
- 页面或 API
- 正常与异常验收场景
- 依赖 Issue 和截止日期

表结构发生变化时，同一个 PR 必须更新模块 ER 图、字段说明和当前 SQL 快照。

## 完成定义

一个 Issue 同时满足以下条件才能关闭：

- 功能符合必做范围和验收条件。
- 页面真实读写 MySQL 数据。
- 数据库约束和 Service 层校验位置清楚。
- 本人完成本地测试并提交证据。
- PR 关联 Issue，且 A 或 B 完成审查。
- 表结构变化已经同步到 ER 图、字段说明和 `schema.sql`。

## 延期处理

```text
在 Issue 写清现象和已尝试内容
→ A 或 B 提供提示或最小示例
→ 原负责人继续完成
→ 删除选做内容
→ 仍影响数据库或主演示链时再由 A 协调
```

延期不能通过增加未经讨论的表、状态或通用框架来解决。
